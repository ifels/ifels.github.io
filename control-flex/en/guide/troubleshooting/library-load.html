Library Load Failures

The log carries a [gamepad-jni] error, or Windows says it cannot verify a publisher — this is that class of failure. The library is two native files, gamepadjni.dll and SDL3.dll; read the log to see which one failed, then work down this page.

Start With the Log

Open logs/latest.log in the instance folder (Prism, HMCL, CurseForge and the vanilla launcher all keep it in the same place) and search for gamepad-jni. Everything this library does — which backend it picked, which file it failed on, whether JNA was even present — is logged under that prefix.

When both backends fail, the four-line block names each half of the problem instead of a single “failed to load native library”: 

[gamepad-jni] no usable gamepad backend (binding=auto)
  JNI: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
  JNA: unavailable - com.sun.jna.Native not on the classpath (this Minecraft version ships no JNA)
  hint: this Minecraft version has no JNA, so only the JNI backend is possible
Line What it means
binding=auto The policy that was used: JNI first, JNA if that fails. jni / jna here means a diagnostic switch was set.
JNI: Why gamepadjni.dll did not load. A Smart App Control block shows up on this line as An Application Control policy has blocked this file.
JNA: Why the JNA backend did not start — or that this Minecraft version carries no JNA at all.
hint: Only present when the cause is recognised. It is the one line worth quoting in a bug report.

Windows 11 Smart App Control Is Blocking gamepadjni.dll

This load failure comes from Windows, not from a wrong mod version, a missing dependency, or a broken download — and it is the most common report from Windows 11 players.

What you see

  • Windows Security pops up a message that it cannot verify the publisher of gamepadjni.dll, usually worded as “Part of this app has been blocked”.
  • The controller disappears completely: Settings → Gamepad Selection is empty, and no button does anything.
  • On some setups the game crashes on startup instead; the crash report then mentions UnsatisfiedLinkError or gamepadjni.dll.
  • In the log, the JNI line ends with An Application Control policy has blocked this file.

Why it happens

Smart App Control (SAC) is a Windows 11 feature, introduced with 22H2. Before a program or a DLL is allowed to run, Windows asks Microsoft's cloud service whether it recognises the file. If the verdict is “safe”, it runs. If the file is unknown and unsigned, it is treated as untrusted and blocked. It is not an antivirus scan and it is not Defender: nothing is quarantined, and no virus is involved.

gamepadjni.dll is unpacked from the mod JAR into %TEMP%\gamepadjni-* at launch. It is a build compiled by this project, it carries no code-signing certificate, and Microsoft's cloud has never seen that exact hash — so SAC cannot make a positive prediction and refuses to load it.

Nothing was deleted or moved to quarantine — the file is still in %TEMP%, and the antivirus history is clean. Unsigned does not mean malicious: almost every Minecraft mod is unsigned. It only means Windows has no way to vouch for this one file.

cfx-gamepadjni is open source. The source is at github.com/ControlFlexMC/cfx-gamepad-jni, and the DLL is built from it in CI. You can audit the code, or follow the README and build the same DLL yourself.

There is no per-file allowlist. Unblocking the file in its Properties, adding the folder to Defender exclusions, or running the launcher as administrator will not help — SAC ignores all three. Its only settings are On, Evaluation and Off, and a blocked file cannot be excepted individually.

From 0.9 (in development): the JNA fallback handles it

0.9 is still in development and has not been released. The automatic fallback described here ships only with Control Flex 0.9 and newer. Until 0.9 is out, 0.8.9 and older still have the JNI backend only — turning SAC off is the only workaround.

Starting with Control Flex 0.9, the bundled cfx-gamepadjni carries two independent backends for the same SDL3 gamepad API: the JNI bridge (gamepadjni.dll, built by this project) and a JNA backend that calls SDL3 directly by symbol name. One JAR, one public API, no setting to change.

The order is fixed: JNI first; if System.load is refused, the library switches to JNA inside the same initialize() call. JNA's own native library, jnidispatch, has been on Minecraft's classpath since 1.8.9 and is used by thousands of programs, so Microsoft's cloud recognises it; gamepadjni.dll is never loaded, and SAC has nothing left to block.

Why not the other way round? Because JNI is faster. Gamepad state is read every tick, on the hot path: JNI is a compiled native bridge, so a Java call lands directly in the C function, while JNA — even with direct mapping — still goes through JNA's dispatch layer on every call. Trying JNI first keeps the default path exactly as cheap as before; JNA only steps in when JNI cannot load.

A successful fallback looks like this in the log — no error, just a warning and the backend that took over: 

[gamepad-jni] JNI backend unavailable: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
[gamepad-jni] binding=jna (SDL3 from ...\Temp\gamepadjni-1234)

That is not a failure state: gamepadjni.dll will not appear in Task Manager, and the controller works normally. The only thing lost is SDL's own log capture, which is diagnostic-only. Every gamepad feature — enumeration, hotplug, rumble, battery, touchpad, sensors — is identical.

What to do

  1. Once 0.9 is released, update to Control Flex 0.9 or newer. 0.8.9 and older have a single backend, so a SAC block means no controller at all, and on some versions a crash. Until then, turning SAC off is the only workaround — see Microsoft: turn off Smart App Control.

    Before turning SAC off, make sure your build has the November 2025 update.

    This is a device-wide setting, not a per-game switch. Turning SAC back on only works after the November 2025 update (Windows 11 25H2 Insider build 26220.7070, KB5070300). It does not disable Defender, but it removes one protection layer. See Microsoft’s Smart App Control FAQ.

  2. On 1.7.10, do one extra step: that Minecraft version ships no JNA, so the fallback has nothing to bind to — see the 1.7.10 section below.
  3. To confirm which backend ran, use the diagnostic switch at the end of this page and compare the two log lines.

Next Step: Code Signing

The plan is to apply for a free open-source code-signing certificate through SignPath Foundation and sign gamepadjni.dll with it. Once signed, the DLL has a verifiable publisher (the certificate is issued to SignPath Foundation), so SAC no longer treats it as unsigned: the JNI path can load normally, and the JNA fallback stays as a safety net. Only gamepadjni.dll is signed; SDL3.dll keeps the same file Minecraft 26.3 ships and is left as is.

Signing is still a plan — it is not done yet, and there is no timeline. SignPath Foundation reviews eligibility (OSI-approved licence, public repository, active maintenance); this page will be updated when there is progress.

Two Libraries: gamepadjni.dll and SDL3.dll

Control Flex unpacks two native libraries from the JAR, and SAC decides per file — so either one can be blocked, not only the one Control Flex builds.

File Role Chance of a SAC block
gamepadjni.dll The JNI bridge that forwards Java calls into SDL3; compiled by Control Flex Higher — unsigned, and Microsoft's cloud has no reputation for this exact hash
SDL3.dll SDL3's gamepad and input layer; both backends bind to it Much lower — it is the same file Minecraft Java 26.3 ships (LWJGL 3.4.3), but still not impossible.

Why SDL3 is much less likely to be blocked. The SDL3.dll in the current Windows build is byte-identical to the LWJGL 3.4.3 SDL3 that Minecraft Java 26.3 loads. SAC accumulates reputation per file hash, and millions of 26.3 clients have already built a reputation for that hash. “Less likely” is not “never”, though: a failed cloud lookup or a stricter system policy can still block it.

SDL3 loads first, then gamepadjni.dll. Because both backends bind to SDL3, a block on SDL3 stops JNI and JNA alike — the 0.9 fallback cannot help.

That failure does not produce the two-backend block above. It is a single line: 

[gamepad-jni] Failed to load native library: ...\Temp\gamepadjni-1234\SDL3.dll: An Application Control policy has blocked this file

If you see this line, SAC blocked SDL3, not gamepadjni.dll.

1.7.10: attach a JNA yourself

Minecraft 1.7.10 has no JNA on its classpath, so the fallback cannot engage even once 0.9 is out. -Djna.library.path does not fix this — that property tells JNA where native libraries are, and it is only read after JNA’s own classes are already loaded.

On the Java 8 runtime that 1.7.10 uses, put a JNA jar where the game class loader can see it: 

-Xbootclasspath/a:C:\path\to\jna-5.12.1.jar

Prism, HMCL and the vanilla launcher all accept that in their JVM arguments field. Keep the path absolute. The option exists only up to Java 8: a 1.7.10 instance started on Java 9+ rejects it, and the jar has to go on the launcher's class path instead.

Any JNA 5.x release works (it is Java 8 bytecode); the core jar is enough, jna-platform is not needed. If JNA cannot unpack its own jnidispatch, point -Djna.boot.library.path at the folder containing jnidispatch.dll.

Architecture Mismatch

If the log shows UnsatisfiedLinkError without the Application Control wording, suspect the architecture first: a 32-bit x86 JVM still asks for the x86_64 directory, and on Windows on ARM an ARM64 JVM finds no native because the JAR ships the x86_64 build only.

Run 64-bit x64 Java on Windows, including Windows on ARM. On Android, see Platform Support for the ABI and launcher requirements.

If it still fails after updating

If there is still no controller after updating, check whether the blocked file is SDL3. That case does not produce the two-backend block above; it is a single Failed to load native library: ...SDL3.dll: An Application Control policy has blocked this file line. SDL3 is a precondition for both backends, so the JNA fallback cannot help.

In that case there is no client-side workaround left. Attach the log and, if you can, the CodeIntegrity event: it will show which file was blocked, and the long-term fix is signing the natives — not something you can do on your side. The report checklist is on the overview page.

Diagnostic Switch

The default is auto. For a bug report — or to prove which half is broken — force one backend and compare: 

-Dcfx.gamepadjni.binding=jni     # JNI only, no fallback (reproduces a Smart App Control block)
-Dcfx.gamepadjni.binding=jna     # JNA only, JNI never attempted
-Dcfx.gamepadjni.binding=auto    # default: JNI, then JNA

jni fails loudly instead of falling back, which is exactly what you want when reproducing the Windows block. jna skips gamepadjni.dll entirely and shows whether the fallback path itself is healthy. The system property wins over the CFX_GAMEPADJNI_BINDING environment variable; values are case-insensitive, and an unrecognised value behaves like auto.

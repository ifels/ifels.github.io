Mod Compatibility

Control Flex is built for modpacks: auto-discovery first, then four escalating tools — the in-game adaptation center, the community config repo, compat JSON, and bridge mods.

Layer One: Auto-Discovery

At startup Control Flex scans Minecraft's KeyMapping registry and registers every non-vanilla binding as a dynamic action. If a mod registered its keys the standard way (JEI recipe keys, combat-mod skills, map hotkeys…), they show up in Key Mapping with no config file at all.

Library mods are exempted automatically (the built-in list covers the Fabric API and Kotlin language-support families), so they never clutter the adaptation lists.

Built-in Compat Configs

A small set of built-in compat configs ships inside the JAR and is extracted to config/controlflex/compat/default/ on every launch:

Mod What it provides
Just Enough Items (JEI) Recipe / uses keys on the GUI layer, plus an ignore list for internal keys that should not be exposed
Epic Fight Battle-mode key and screen rules; points to the official cfx-compat-epicfight bridge
Nightfall Key and screen adaptation for the mod

Everything else is covered by auto-discovery or the community repo; built-in configs only activate when their target mod is actually installed and loaded.

Layer Two: In-Game Mod Adaptation

Open Control Flex Settings → Mod Adaptation: every installed mod is listed with name, icon, and version. Open a mod to work in three tabs:

Tab Purpose
Key Bindings The mod's discovered actions; assign layers (Main / Screen / Overlay) and bind controller buttons
Screen Adaptation Stick mode, layer mapping, and cursor rules while that mod's GUI is open
Overlay Adaptation The same for interactive HUDs (spell wheels, radial menus, photo HUDs)

To add a Screen or Overlay rule: open the target GUI or HUD once in-game so Control Flex records it, then use + Add Screen/Overlay Adaptation in the mod's detail page and pick it from the recent-pages list (up to 50). Entries that could not be matched to a mod can be scanned automatically.

Each stick can use a different behavior for that page:

Behavior What it does
Independent Stick directions are actions bound on Layer Mapping; the default on Overlay and for the Screen right stick
Radial Path Stick traces a path / angle — spell wheels and radial-menu style UIs
Virtual Mouse Stick moves a cursor inside that UI; the default for the Screen left stick

With no rule: Screen uses Virtual Mouse on the left stick and Independent on the right; Overlay keeps both sticks Independent (the layer's four-way bindings). Cursor style can be system / Bedrock / hand; Virtual Mouse has cursor speed, and Radial Path has threshold, radius, angle bias, and whether the stick restores its last angle.

Rule edits are copy-on-write: packaged and community files stay read-only and changes land in config/controlflex/compat/user/; a mod's Reset Config restores its packaged or applied community default.

Layer Three: Community Configs

The official community source is ControlFlexMC/cfx-compat-configs. From Mod Adaptation, hit Sync Configs, browse variants, preview Bindings / Screen / Overlay, and Apply — any existing user file is backed up first. Extra sources can be added, and local JSON can be imported/exported from a mod's detail page. PRs for new mod configs are welcome.

Layer Four: Compat JSON (pack authors & power users)

JSON is the shareable unit behind the UI. Drop files at config/controlflex/compat/user/{mod_id}.json; bridge mods may install theirs into compat/mods/ (read-only at runtime). A config can:

  • Place keys on Main / Screen / Overlay (inGameKeys / screenKeys / overlayKeys).
  • Choose a dispatch channel per key (KeyMapping, Forge event bus, GLFW-compat polling, screen input).
  • Ignore unused keys (ignoreKeys), suppress keys while holding an item (itemSuppressKeys), and attach tips.
  • Declare per-screen / per-overlay stick maps (Independent / Radial Path / Virtual Mouse, same options as the UI).

Example shape (excerpted fields showing layer placement and state coupling): 

{
  "mod_id": "epicfight",
  "mod_name": "Epic Fight",
  "home_page": "https://www.curseforge.com/minecraft/mc-mods/epic-fight-mod",
  "ignoreKeys": ["key.epicfight.dodge"],
  "inGameKeys": ["epicfight:key.epicfight.attack"],
  "screenKeys": [],
  "overlayKeys": [],
  "itemSuppressKeys": [{
    "item": "mymod:special_weapon",
    "playerState": ["mymod:combat_mode"],
    "suppressActions": ["attack"]
  }]
}

For the full field set and allowed values, see the authoritative reference: cfx-compat-configs field reference (English) / 中文.

playerState conditions work together with states pushed by bridge mods (IPlayerStateRegistry, keys shaped modId:stateName) — see the developer docs for the bridge side.

Custom Input Systems: Bridge Mods

If a mod bypasses KeyMapping, has runtime combat state, or reads the gamepad directly, it needs a bridge mod using the IControlFlexPlugin SPI: export compat JSON, push player states, react to controller lifecycle events. The official example is cfx-compat-epicfight (which the built-in Epic Fight file points to). Start at API Quick Start.

Still Misbehaving? Check in This Order

  1. Check Key Mapping — is the action on the right layer (Screen vs Overlay vs Main)?
  2. Open Mod Adaptation for that mod — add a Screen/Overlay rule, or apply a community config.
  3. If the mod only listens for physical keys, bind it with Virtual KBM.
  4. Hand-edit or share a compat JSON; write a bridge if the mod bypasses KeyMapping entirely.

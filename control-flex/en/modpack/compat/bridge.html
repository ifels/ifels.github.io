Bridge Mods & the Developer API

compat JSON can only adjust things that already exist — a registered KeyMapping, a dispatched key, an open screen. When a mod builds its own input system you have to plug in on the Java side: that is a bridge mod. This page is the single entry point for bridge development — whether to write code at all, then the API, the skeleton, the interface reference, every official implementation, and shipping.

On this page: Decide first · API setup · Plugin skeleton · Interface reference · Official bridges · Five techniques · Debug & ship

1. First: do you actually need code?

Compat JSON can Only a bridge mod can
Place registered keys on Main / Screen / Overlay Make keys that never registered a KeyMapping appear in the binding list
Choose the dispatch channel (including the GLFW polling mirror) Reach mods that call GLFW.glfwGetKey directly (the GLFW layer cannot be injected)
Suppress actions by main-hand item plus player state Push the mod's runtime state into Control Flex for use as a condition
Phase persistence, ignored keys, tips, per-screen stick parameters Announce that a mod has taken over an overlay or the camera, so stick and look behavior can switch
Fall back to virtual keyboard / mouse for mods that only see physical keys Run fully custom logic off the stick axes (vehicle steering, camera), or forward an action into the mod's own function

One-line test: if the mod's keys show up under Key Mapping → that mod, you do not need a bridge; if they do not, you do. The three tools are cumulative — auto-discovery → compat JSON → bridge; do not skip the first two and start writing code.

2. Wiring up control-flex-api

  • A separate repository, ControlFlexMC/control-flex-api, published through JitPack; currently 0.9.0.
  • The artifact is Java 8 bytecode (class 52), so it loads on any JVM 8+; a bridge mod does not have to share the core mod's toolchain.
  • compileOnly only: Control Flex provides it at runtime. Do not bundle the API into your jar.
  • Scope: read controller input, query action states, push mod states, declare interactive overlays, take over the camera, install compat / guide assets.
// build.gradle
repositories { maven { url 'https://jitpack.io' } }

dependencies {
    compileOnly 'com.github.ControlFlexMC:control-flex-api:0.9.0'
    compileOnly 'org.jetbrains:annotations:24.0.1'
}
# mods.toml (Forge / NeoForge)
[[dependencies.your_mod_id]]
    modId = "controlflex"
    mandatory = true
    versionRange = "[0.8.8,)"
    ordering = "AFTER"
    side = "CLIENT"

# fabric.mod.json (Fabric)
{ "depends": { "controlflex": ">=0.8.8" } }

The first line is always an availability check — Control Flex may not be installed, and SDL3 may have failed to initialize. Every provider can be null. 

if (!ControlFlexApi.isAvailable()) {
    return;   // Control Flex missing or not initialized: skip every controller path
}

3. Plugin skeleton: IControlFlexPlugin

Callback When it runs / what it is for
getModId() Plugin identifier, used for logging and de-duplication.
onInstallCompatConfigs() Called before ready; use installer.install() to install compat JSON into compat/mods/.
onInstallGuideAssets() Same idea, into guides/mods/.
onControlFlexReady() The single initialization callback; every provider is ready at this point.
onControllerConnectionChanged() Fires when a controller connects or disconnects.
cameraLookConsumer() Return an ICameraLookConsumer to take over each frame's look delta (0.8.8+, see camera takeover); null means no takeover.
requireApiVersion() Default method that checks the minimum API version and returns false when unmet. 
package com.example.mymod;

import com.ifels.controlflex.api.*;

public class MyPlugin implements IControlFlexPlugin {

    @Override
    public String getModId() { return "my_bridge_mod"; }

    @Override
    public void onInstallCompatConfigs(ICompatAssetInstaller installer) {
        installer.install("/assets/my_bridge_mod/compat/targetmod.json", "targetmod.json");
    }

    @Override
    public void onControlFlexReady() {
        if (!requireApiVersion("0.8.8")) return;
        if (!ControlFlexApi.isAvailable()) return;

        ControlFlexApi.getPlayerStateRegistry().setState("mymod:initialized", true);
    }
}

Registration goes through an SPI services file; Control Flex discovers plugins automatically: 

src/main/resources/META-INF/services/com.ifels.controlflex.api.IControlFlexPlugin

com.example.mymod.MyPlugin

Discovery and callback order (this decides what you can do in which callback): 

Control Flex startup
  └── initializeClient()
        ├── providers injected  → isAvailable() becomes true
        └── built-in configs extracted to default/

  └── onKeyMappingsReady()
        └── discover SPI plugins
              ├── new CompatAssetInstaller(plugin.class, compatDir)
              ├── plugin.onInstallCompatConfigs(installer)
              ├── new CompatAssetInstaller(plugin.class, guideDir)
              ├── plugin.onInstallGuideAssets(installer)
              └── plugin.onControlFlexReady()

  runtime
        ├── plugin.onControllerConnectionChanged(connected)
        └── plugin.cameraLookConsumer().consumeLook(yaw, pitch)   // per frame, if non-null

Installed JSON lands in compat/mods/: above default/, below user/ — so players can still override your defaults in the user layer, a bridge never locks them out. A same-named file is replaced wholesale; there is no field-level merge.

4. Interface reference

Package com.ifels.controlflex.api, 13 public types. Everything except IPlayerStateRegistry.setState() must be called on the client main thread.

Type Purpose

IControlFlexPluginSPI plugin interface (lifecycle callbacks)
ICompatAssetInstallerAsset installer (only usable inside the matching callback)
IActionStateProviderQuery whether an action is currently active
IInputProviderController connection state and hardware view
IControllerStateLive view of sticks / triggers / buttons
IControllerCapabilitiesHardware capabilities (type, paddles, gyro, rumble)
ButtonNameButton and axis name constants
IPlayerStateRegistryPush modId:state states for JSON to consume
IInteractiveContextRegistrarDeclare an interactive overlay's foreground / background
ICameraLookConsumerTake over each frame's look delta (when a mod owns the camera)

IActionStateProvider

boolean isGameActionActive(String actionId)   // game layer (no screen open)

Three action ID forms:

  • Built-in actions: attack, use, jump, sneak, move_forward …
  • Vanilla keys: key.jump, key.sneak
  • Mod keys: epicfight:key.epicfight.attack (modId:keyName; the key name carries no modid: prefix)

IInputProvider · IControllerState · ICapabilities

float getLeftStickX()  / getLeftStickY()

ButtonName gives three groups: buttons (A…Y, DPAD_UP, LEFT_BUMPER, LEFT_TRIGGER, LEFT_STICK_CLICK, BACK, START, GUIDE, PADDLE_1…PADDLE_4, TOUCHPAD), stick directions (LEFT_STICK_UP …) and axes (AXIS_LEFT_X, AXIS_RIGHT_TRIGGER …).

IPlayerStateRegistry

void setState(String stateKey, boolean active)  // thread-safe, callable from any thread
boolean getState(String stateKey)               // client thread
void clearState(String stateKey)                // drop the registration

stateKey is modId:stateName (e.g. epicfight:battle_mode) — exactly the string compat JSON reads in itemSuppressKeys[].playerState.

ICameraLookConsumer (0.8.8+)

boolean consumeLook(float yaw, float pitch)
// true  = this frame's look is consumed: Control Flex must not write player rotation
// false = not consumed: Control Flex keeps its normal path
  • Why: a mod has taken over the rendered camera (Epic Fight's TPS combat camera, lock-on, …), so the player's yRot/xRot is no longer what you see; the look delta has to be handed to that mod.
  • Called at most once per frame; the arguments are deltas calibrated before turning, the same scale the vanilla mouse pipeline hands to the mod that took over.
  • Override cameraLookConsumer() in your plugin and return an implementation; returning null (the default) means no takeover.

IInteractiveContextRegistrar

void notifyOverlayForeground(String className)   // overlay entered the foreground
void notifyOverlayBackground(String className)   // overlay went back (pairs with foreground)
void clearAll()                                  // fallback: world unload / mod shutdown

className is the fully qualified class name — Control Flex looks it up in the compat JSON overlay table to resolve stick and cursor behavior. Null-check first: getInteractiveContextRegistrar() may be null.

ICompatAssetInstaller

boolean install(String resourcePath, String fileName)
// resourcePath: classpath path inside your jar, e.g. "/assets/mymod/compat/targetmod_keys.json"
// fileName:     target file name inside compat/mods/ or guides/mods/
// returns:      true when installed

5. The official implementations

Compatibility work comes in three kinds, all under the ControlFlexMC org: the core mod (built-in JSON + dispatch channels), the config source (distribution of community JSON), and bridges — the 5 that actually write Java.

Repository Adapts Branches · loaders Technique
control-flex Every standard KeyMapping mod Core mod, every version line 3 built-in JSON files + five dispatch channels + three-layer override
cfx-compat-configs Mods plain JSON can cover Tagged per ControlFlex release Community config source, see Compat JSON
cfx-compat-epicfight Epic Fight 1.20.1 Forge · 1.21.1 NeoForge Registers as EF's controller mod + mixin rewrites binding lookup + state push + camera takeover
cfx-compat-create Create train console 1.20.1 Forge / Fabric · 1.21.1 NeoForge A single injection point that merges movement impulses into key checks
cfx-compat-exposure Exposure viewfinder 1.20.1 Forge / Fabric · 1.21.1 Fabric / NeoForge Declares an interactive overlay's foreground / background
cfx-compat-emi EMI 1.18.2 / 1.19.2 / 1.20.1 / 1.21.1 Registers 22 pseudo KeyMappings and forwards them into EMI's own functions
cfx-compat-vehicles Immersive Vehicles (MTS) and other GLFW-polling vehicle mods 1.12.2 → 1.21.1, 26.1.2 (Forge line) Mixin inside the vehicle mod's own key read path

cfx-compat-epicfight: making Control Flex EF's controller backend

Epic Fight does not read KeyMapping; it has its own input SPI (IEpicFightControllerMod). With nothing registered it falls back to raw GLFW keyboard state, which a gamepad binding can never satisfy. It also looks up a ControllerBinding per action, and only the implementor can supply that object — JSON cannot.

So the bridge does three things: implements IEpicFightControllerMod (stick → PlayerInputState, actions → ControllerBinding); mixins over EF's controllerBinding() to redirect binding lookup into Control Flex's action state; listens for ChangePlayerModeEvent and pushes epicfight:battle_mode. On top of that, EpicFightCameraBridge implements camera takeover — turn deltas go to EpicFightCameraAPI.turnCamera(), so the view tracks the stick while EF owns the camera (TPS combat camera, lock-on).

Requires ControlFlex ≥ 0.8.8; Epic Fight ≥ 20.14 (1.20.1 Forge) / ≥ 21.15 (1.21.1 NeoForge). Incompatible with Controlify — both want to be EF's controller mod and only one can win. Source entry points: CfxEpicFightControllerMod, EpicFightStateBridge, EpicFightCameraBridge, mixin/EpicFightInputActionMixin.

cfx-compat-create: one injection point for train throttle

Create's train console does not read KeyMapping.isDown(); it walks all the way down to InputConstants.isKeyDown(window, code). Control Flex's analog movement takes over the MOVE group — those actions stop being dispatched and the stick value goes straight into player.input.forwardImpulse — so the player walks, but no key press is ever published and the train never gets throttle.

The fix is deliberately minimal: a single RETURN injection on ControlsUtil.isActuallyPressed(KeyMapping) merges forwardImpulse / leftImpulse into the forward / back / left / right checks; sneak → brake, jump → horn. When the real key is already down the original result is returned untouched, so keyboard priority survives.

Note it writes no global state: no synthetic GLFW poll state, no KeyMapping writes, no Forge key events, so other mods are unaffected. It needs no "is the player driving?" check either, because only the train console calls isActuallyPressed. Source entry points: CreateTrainControl, mixin/ControlsUtilMixin.

cfx-compat-exposure: context declaration only

Exposure's viewfinder is an interactive overlay that grabs the camera and hides the HUD. Control Flex only switches stick behavior for contexts it knows about, so the bridge just reports: mixins on CameraClient.setupViewfinder / removeViewfinder — the two chokepoints every open/close path goes through — call notifyOverlayForeground / notifyOverlayBackground.

The detail is in pairing: the bridge keeps its own foreground flag, so removeViewfinder without an active viewfinder never emits a stray background; switching cameras emits background → foreground in that order; logging out resets state and emits one final background. Requires ControlFlex ≥ 0.8.7 (0.8.7 renamed these two methods) and Exposure ≥ 1.9.20.

cfx-compat-emi: 22 pseudo KeyMappings

EMI stores its keybinds in its own config (binds.*) and matches them inside its own screens — it registers no Minecraft KeyMapping, so its actions appear neither in vanilla Controls nor in controller auto-discovery. The bridge registers 22 pseudo KeyMappings for Control Flex to discover and forwards each press into EMI's own interaction functions: no fake input, and EMI's key settings are left untouched.

Group Actions
ScreenToggle EMI, focus search, clear search
BrowseView recipes / uses, add to favourites, recipe tree, stack tree, forward / back
CraftCraft one / a stack, to inventory (one / stack), to cursor (one)
CreativeCheat one / a stack to inventory or cursor
ManageHide item, hide by ID, copy recipe ID

All of them live in the GUI layer and show up as "Control Flex x EMI" in the binding list. Most act on the hovered stack, so point at the item first; while a text field has focus, or EMI is switched off or reloading, only "Toggle EMI" fires. Not supported: defaultStack, deleteCursorStack, showCraft (the first two are inline logic deep inside the recipe screen, the third is a held state rather than an action), displayAllRecipes (not in the released jar), and "Copy Recipe ID" on a recipe screen (its context sits in a private field). It never rewrites EMI's own binds.* either.

cfx-compat-vehicles: vehicles only speak GLFW

Immersive Vehicles (MTS) reads input through GLFW.glfwGetKey(window, keyCode) — it looks at neither KeyMapping nor InputConstants, so keyMapping / virtualKbm / glfwPoll all fail to reach it. The GLFW layer itself is not injectable on Forge (library classes are loaded by the system class loader and never pass through ModLauncher), so the mixin has to sit in the vehicle mod's own read path: InterfaceInputMixin hooks mcinterface1201.InterfaceInput#isKeyPressed and answers true for the four movement keys.

The signal is still the player's own forwardImpulse / leftImpulse (including the analog response curve), falling back to action states when they are zero, so it keeps working with analog movement off; nothing is polled, no global key state is written, and a physically pressed key always wins. It ships no JSON: it reads the core mod's signals directly, so there is no rule set to keep in sync with the config format. Known limits: IV's own keybinds (car.gas, …) are ignored, so reset them to WASD if you changed them; do not bind IV's built-in joystick, which sets kbOverride and disables the bridge; the mixin targets a version-stamped package (mcinterface1201), so another MC version needs its own build.

Bridge and JSON are not either/or: most bridges also install a JSON file into the mods/ layer in onInstallCompatConfigs — letting JSON decide where keys go and Java decide what happens at runtime. In the community source the create / emi configs go the other way and use dependencies to require the bridge.

6. Five techniques, five real examples

1) Keys are not registered at all: add pseudo KeyMappings (EMI)

Register ordinary KeyMappings so auto-discovery sees them, then forward the press into the mod's own entry point — no fake input, no changes to the mod's key settings. 

// Register a pseudo key mapping (registration API differs per MC version / loader)
new KeyMapping("key.cfx_target.open", GLFW.GLFW_KEY_K, "key.categories.cfx_target");

// Each tick, forward Control Flex's action state into the mod's own entry point
if (ControlFlexApi.getActionStateProvider()
        .isGameActionActive("cfx_target:key.cfx_target.open")) {
    TargetMod.openPanel();   // call the mod's function, do not synthesize a key press
}

2) The mod reads raw key state: mixin into its read point (vehicles / Create)

The glfwPoll channel covers polling through InputConstants.isKeyDown, but mods that call GLFW.glfwGetKey never see it — GLFW is loaded by the system class loader and never passes through ModLauncher's transformer. Instead, put a mixin on the mod's own read entry point and answer "is it held right now". 

// Only answer for the four movement keys; everything else keeps the original logic
@Mixin(TargetInput.class)
public abstract class TargetInputMixin {

    @Inject(method = "isKeyPressed", at = @At("HEAD"), cancellable = true)
    private void cfx$steering(int keyCode, CallbackInfoReturnable<Boolean> cir) {
        if (ControlFlexApi.isAvailable()
                && ControlFlexApi.getActionStateProvider().isGameActionActive("move_forward")) {
            cir.setReturnValue(true);
        }
    }
}

Keeping that mixin inside a separate bridge mod keeps the core free of third-party dependencies, and a failure only affects that one compat package.

3) The mod has runtime state: push a state and let JSON consume it (Epic Fight)

Epic Fight's battle mode decides which keys the mod should own. Java only pushes the state; which actions get suppressed is written in JSON — so players and pack authors can change it. 

// Java: push once whenever the state flips
ControlFlexApi.getPlayerStateRegistry()
    .setState("epicfight:battle_mode", inBattle);
// JSON: consume it as a condition (holding a katana in battle mode: suppress generic use)
"itemSuppressKeys": [
  { "item": "efn:yamato_dmc*",
    "playerState": ["epicfight:battle_mode"],
    "suppressActions": ["use"] }
]

4) Custom overlays: declare foreground / background (Exposure)

A self-drawn HUD is not a Screen, so Control Flex cannot see it. Report once on open and once on close and the core mod switches stick and cursor behavior in the Overlay phase using the JSON overlay table; the class name must match the overlay key. 

public final class OverlayNotifier {

    public static void onOpened(Object overlay) {
        IInteractiveContextRegistrar registrar = ControlFlexApi.getInteractiveContextRegistrar();
        if (registrar != null) {
            registrar.notifyOverlayForeground(overlay.getClass().getName());
        }
    }

    public static void onClosed(Object overlay) {
        IInteractiveContextRegistrar registrar = ControlFlexApi.getInteractiveContextRegistrar();
        if (registrar != null) {
            registrar.notifyOverlayBackground(overlay.getClass().getName());
        }
    }
}

Paired notifications are mandatory: foreground without background leaves stick behavior stuck in overlay mode; use clearAll() as the fallback when leaving the world.

5) A mod took the camera: consume the look delta

Once the camera is taken over, writing yRot/xRot changes nothing on screen. Implement ICameraLookConsumer and hand the delta to whoever owns the camera; returning true means the frame is consumed and the core mod will not write player rotation. 

@Override
public ICameraLookConsumer cameraLookConsumer() {
    return (yaw, pitch) -> {
        if (!ControlFlexApi.isAvailable()) return false;
        return TargetCameraApi.getInstance().turnCamera(yaw, pitch);
    };
}

7. Debugging and shipping

  • Log prefix [ModCompat]: config loading, overriding and skip reasons all land there; use your own logger for bridge messages (LogManager.getLogger("my-mod-id")).
  • Guard the minimum API version with requireApiVersion("0.8.8"), and declare Control Flex as a mandatory dependency in mods.toml / fabric.mod.json.
  • API is compileOnly; ship a separate JAR and do not shade it in, or you duplicate the core.
  • Keep the target mod compileOnly too (CurseForge Maven / Modrinth Maven), and add a path that exits quietly when it is missing — that is how the vehicle bridge stays optional.
  • Multi-loader projects use three modules, common/ + forge/ + fabric/: logic in common, mixin config and mod metadata per loader.
  • When you publish, state what it fixes, which mod versions and loaders you tested, whether it ships optional JSON defaults, and which mods it conflicts with.

库加载失败

日志里出现 [gamepad-jni] 报错，或 Windows 弹窗说无法确认发布者 —— 就是这一类。这个库由两个原生文件组成：gamepadjni.dll 和 SDL3.dll；先读日志确认是哪一个失败，再按顺序往下排查。

先看日志

打开实例目录下的 logs/latest.log（Prism、HMCL、CurseForge、官方启动器都在同一位置），搜 gamepad-jni。这个库做了什么 —— 选了哪条后端、卡在哪个文件、JNA 在不在 —— 都写在这个前缀下。

两套后端都失败时，日志会一次写清两半各自的原因，而不是只有一句「加载原生库失败」： 

[gamepad-jni] no usable gamepad backend (binding=auto)
  JNI: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
  JNA: unavailable - com.sun.jna.Native not on the classpath (this Minecraft version ships no JNA)
  hint: this Minecraft version has no JNA, so only the JNI backend is possible
行 含义
binding=auto 这一次用的策略：先 JNI，失败再 JNA。这里显示 jni / jna 说明手动指定过后端。
JNI: gamepadjni.dll 为什么没加载。智能应用控制的拦截就出现在这一行，末尾是 An Application Control policy has blocked this file。
JNA: JNA 后端为什么没起来 —— 或者这一版 Minecraft 根本没有 JNA。
hint: 只在认出原因时出现。写报告时，这一行最值得贴。

Windows 11 智能应用控制拦截了 gamepadjni.dll

这类加载失败来自 Windows，而不是模组版本装错、缺少前置或下载损坏 —— 也是 Windows 11 上最常见的一类报障。

你会看到什么

  • Windows 安全中心弹窗，说无法确认 gamepadjni.dll 的发布者，措辞通常是「此应用的一部分已被阻止」。
  • 手柄彻底消失：设置 → 手柄选择里是空的，按键也没有任何反应。
  • 有些环境则会启动即崩溃；崩溃报告里会出现 UnsatisfiedLinkError 或 gamepadjni.dll 字样。
  • 日志里，JNI 那一行以 An Application Control policy has blocked this file 结尾。

为什么会这样

智能应用控制（SAC）是 Windows 11 22H2 引入的功能。程序或 DLL 运行之前，Windows 会先问微软的云服务是否信任这个文件：判定安全就放行；文件没名气、又没有签名，就按「不受信任」拦下。它不是杀毒扫描，也不是 Defender —— 没有文件被隔离，更不代表有病毒。

gamepadjni.dll 是启动时从模组 JAR 解压到 %TEMP%\gamepadjni-* 的。它由 Control Flex 自己编译，没有代码签名证书，微软云端也没有这个哈希的信誉记录 —— SAC 无法给出正面判断，于是拒绝加载。

文件没有被删除，也没有进隔离区 —— 它还在 %TEMP% 里，杀软历史是干净的。未签名不等于有毒：绝大多数 Minecraft 模组都没有签名。它只说明 Windows 没法为这一个文件背书。

cfx-gamepadjni 是开源的。源码在 github.com/ControlFlexMC/cfx-gamepad-jni，DLL 由 CI 从这份源码构建。你可以直接审计代码，也可以按 README 在本地编译出同一个 DLL 来比对。这个库不含任何恶意代码；随着用户量增长、这个哈希在微软云端的信誉逐渐累积，后续也有机会被 SAC 判为可信 —— 但这只是一种可能，代码签名仍是更确定的解法。

没有单文件白名单。在文件属性里「解除锁定」、把目录加进 Defender 排除项、用管理员身份启动 —— 这三样都没用，SAC 都不看。它只有「打开 / 评估 / 关闭」三个状态，被拦的文件不能单独放行。

0.9 起（开发中）：自动改用 JNA

0.9 仍在开发中，尚未发布。下面这套自动回退只随 Control Flex 0.9 及之后的版本提供。在 0.9 发布之前，0.8.9 及更早版本仍然只有 JNI 一条后端 —— 关闭 SAC 是唯一的临时办法。

从 Control Flex 0.9 起，随包的 cfx-gamepadjni 在同一个 JAR 里带了两套独立后端：JNI（gamepadjni.dll，由 Control Flex 自己编译）和按符号名直接调用 SDL3 的 JNA。一个 JAR、一套公开 API，不需要改任何设置。

顺序是固定的：先试 JNI，如果 System.load 被拒绝，就在同一次 initialize() 里改用 JNA。JNA 自己的原生库 jnidispatch 从 1.8.9 起就在 Minecraft 的 classpath 上，被成千上万的程序用过，微软云端有它的信誉记录。

为什么不是反过来？因为 JNI 的性能更好。手柄状态每 tick 都要读，属于热路径：JNI 是编译好的原生桥，Java 调用直接落到 C 函数；JNA 即使走 direct mapping，每次调用仍要经过 JNA 的分发层。让 JNI 先上，默认路径的开销就和以前完全一致；JNA 只在 JNI 加载不了时兜底。

回退成功时，日志长这样 —— 不是报错，只有一条警告和最终接手的那条后端： 

[gamepad-jni] JNI backend unavailable: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
[gamepad-jni] binding=jna (SDL3 from ...\Temp\gamepadjni-1234)

这不是故障状态：任务管理器里不会出现 gamepadjni.dll，手柄照常工作。唯一少掉的是 SDL 自己的日志捕获，那只是诊断信息。枚举、热插拔、震动、电量、触摸板、传感器，全都一样。

你该做什么

  1. 0.9 发布后，更新到 Control Flex 0.9 或更新版本。0.8.9 及更早只有一条后端，被 SAC 拦下就等于完全没有手柄，部分版本还会崩溃。在 0.9 发布之前，关闭 SAC 是唯一的临时办法 —— 具体步骤见微软官方：关闭智能应用控制。

    关闭 SAC 前，先确认系统装了 2025 年 11 月的更新。

    这是设备级的选择，不是给某个游戏开的开关。只有装了 2025 年 11 月的更新（Windows 11 25H2 Insider 26220.7070 / KB5070300），关闭 SAC 后才能重新打开。它不会关闭 Defender，但确实少了一层防护。详见微软官方的智能应用控制常见问题。

  2. 1.7.10 要多做一步：这一版 Minecraft 不带 JNA，回退没有东西可绑 —— 见下面的 1.7.10 小节。
  3. 想确认实际走的是哪条后端，用本页末尾的诊断开关，对比两行日志。

下一步计划：代码签名

计划通过 SignPath Foundation 申请免费的开源代码签名证书，再用它对 gamepadjni.dll 签名。签名之后，这个 DLL 有可验证的发布者（证书签发给 SignPath Foundation），SAC 不再把它当成未签名文件，JNI 路径就能正常加载，JNA 回退只留作兜底。只签 gamepadjni.dll 本身；SDL3.dll 继续保持与 Minecraft 26.3 相同的文件，不动它。

签名还在计划阶段，尚未完成，也没有确定的时间表。SignPath Foundation 会审核项目资格（开源许可证、公开仓库、仍在维护等）；有进展会更新这里。

两个库：gamepadjni.dll 与 SDL3.dll

Control Flex 从 JAR 里解压两个原生库。SAC 是按文件逐个判断的，所以被拦的可能是其中任意一个，不一定总是 Control Flex 自己编译的那个。

文件 作用 被 SAC 拦的可能
gamepadjni.dll JNI 桥，把 Java 调用转给 SDL3；由 Control Flex 自己编译 较高 —— 未签名，微软云端没有这个哈希的信誉记录
SDL3.dll SDL3 的手柄 / 输入层；两套后端都绑定它 低很多 —— 与 Minecraft Java 26.3 随包的是同一个文件（LWJGL 3.4.3）；但仍不排除被拦的可能。

为什么 SDL3 被拦的可能性低很多。目前 Windows 包里这份 SDL3.dll 与 Minecraft Java 26.3 加载的 LWJGL 3.4.3 版本字节相同。SAC 的云端信誉按文件哈希累积，几百万个 26.3 客户端已经替这个哈希积累了信誉。但「可能性低」不等于「不会」：云端判断失败或系统策略更严时，仍然可能拦它。

加载顺序是 SDL3 先、gamepadjni.dll 后。SDL3 是两套后端共同的前置，所以它一旦被拦，JNI 和 JNA 都起不来，0.9 的回退也帮不上。

这种失败不会出现上面的双后端失败块，而是单独一行： 

[gamepad-jni] Failed to load native library: ...\Temp\gamepadjni-1234\SDL3.dll: An Application Control policy has blocked this file

看到这一行，说明被拦的是 SDL3，不是 gamepadjni.dll。

1.7.10：自己挂一个 JNA

Minecraft 1.7.10 的 classpath 上没有 JNA，所以即使 0.9 发布，回退也无法生效。-Djna.library.path 解决不了这个问题 —— 那个属性只是告诉 JNA 原生库在哪，而且要在 JNA 的类已经加载之后才会读。

在 1.7.10 使用的 Java 8 上，把 JNA 的 jar 放到游戏类加载器能看见的位置： 

-Xbootclasspath/a:C:\path\to\jna-5.12.1.jar

Prism、HMCL 和官方启动器都接受把它写进 JVM 参数。路径要用绝对路径。这个选项只存在到 Java 8：用 Java 9+ 启动的 1.7.10 会直接拒绝，只能把 jar 放进启动器的 classpath。

任意 JNA 5.x 版本都可以（都是 Java 8 字节码）；核心 jar 就够，不需要 jna-platform。如果 JNA 解压不出自己的 jnidispatch，再用 -Djna.boot.library.path 指向存放 jnidispatch.dll 的目录。

架构不匹配

日志里出现 UnsatisfiedLinkError、又没有 Application Control 字样时，先怀疑架构：32 位 x86 的 JVM 仍会按 x86_64 去找库；Windows on ARM 上如果用 ARM64 的 JVM，而 JAR 里只有 x86_64 版本，同样找不到。

Windows 上一律用 64 位 x64 Java（含 Windows on ARM）。Android 的 ABI 与启动器要求见平台支持。

更新后还是失败呢

如果更新后还是没有手柄，先看日志里被拦的是不是 SDL3。这种情况不会出现上面的双后端失败块，而是只有一行 Failed to load native library: ...SDL3.dll: An Application Control policy has blocked this file。SDL3 是两套后端共同的前置，JNA 回退也帮不上。

这种情况客户端已经没有绕法了。把日志和能捞到的 CodeIntegrity 事件一并附上：它会写明被拦的是哪个文件；长期解法是给原生库做代码签名，这不是你这边能做的。报障清单在概览页。

诊断开关

默认是 auto。写报告时 —— 或者想证明到底哪一半坏了 —— 可以强制走一条后端再对比： 

-Dcfx.gamepadjni.binding=jni     # JNI only, no fallback (reproduces a Smart App Control block)
-Dcfx.gamepadjni.binding=jna     # JNA only, JNI never attempted
-Dcfx.gamepadjni.binding=auto    # default: JNI, then JNA

jni 会直接失败而不是回退，正好用来复现 Windows 的拦截。jna 完全跳过 gamepadjni.dll，用来看回退路径本身是否健康。系统属性优先于 CFX_GAMEPADJNI_BINDING 环境变量；大小写不敏感，不认识的值按 auto 处理。

手柄根本没被识别？看手柄未被识别。游戏启动就崩？看启动崩溃。报障清单在概览页。

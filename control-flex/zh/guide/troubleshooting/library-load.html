库加载失败

日志里出现 [gamepad-jni] 报错，或 Windows 弹窗说无法确认 gamepadjni.dll 的发布者 —— 就是这一类。先读日志，再按顺序往下排查。

先看日志

打开实例目录下的 logs/latest.log（Prism、HMCL、CurseForge、官方启动器都在同一位置），搜 gamepad-jni。这个库做了什么 —— 选了哪条后端、卡在哪个文件、JNA 在不在 —— 都写在这个前缀下。

两套后端都失败时，日志会一次写清两半各自的原因，而不是只有一句「加载原生库失败」： 

[gamepad-jni] no usable gamepad backend (binding=auto)
  JNI: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
  JNA: unavailable - com.sun.jna.Native not on the classpath (this Minecraft version ships no JNA)
  hint: this Minecraft version has no JNA, so only the JNI backend is possible
行 含义
binding=auto 这一次用的策略：先 JNI，失败再 JNA。这里显示 jni / jna 说明手动指定过后端。
JNI: 我们自己的 gamepadjni.dll 为什么没加载。智能应用控制的拦截就出现在这一行，末尾是 An Application Control policy has blocked this file。
JNA: JNA 后端为什么没起来 —— 或者这一版 Minecraft 根本没有 JNA。
hint: 只在认出原因时出现。写报告时，这一行最值得贴。

Windows 11 智能应用控制拦截了 gamepadjni.dll

这类加载失败来自 Windows，而不是模组版本装错、缺少前置或下载损坏 —— 也是 Windows 11 上最常见的一类报障。

你会看到什么

  • Windows 安全中心弹窗，说无法确认 gamepadjni.dll 的发布者，措辞通常是「此应用的一部分已被阻止」。
  • 手柄彻底消失：设置 → 手柄选择里是空的，按键也没有任何反应。
  • 有些环境则会启动即崩溃；崩溃报告里会出现 UnsatisfiedLinkError 或 gamepadjni.dll 字样。
  • 日志里，JNI 那一行以 An Application Control policy has blocked this file 结尾。

为什么会这样

智能应用控制（SAC）是 Windows 11 22H2 引入的功能。程序或 DLL 运行之前，Windows 会先问微软的云服务认不认识这个文件：判定安全就放行；文件没名气、又没有签名，就按「不受信任」拦下。它不是杀毒扫描，也不是 Defender —— 没有文件被隔离，更不代表有病毒。

我们的 gamepadjni.dll 是启动时从模组 JAR 解压到 %TEMP%\gamepadjni-* 的。它由我们自己编译，没有代码签名证书，微软云端也没见过这个哈希 —— SAC 无法给出正面判断，于是拒绝加载。

文件没有被删除，也没有进隔离区 —— 它还在 %TEMP% 里，杀软历史是干净的。未签名不等于有毒：绝大多数 Minecraft 模组都没有签名。它只说明 Windows 没法为这一个文件背书。

没有单文件白名单。在文件属性里「解除锁定」、把目录加进 Defender 排除项、用管理员身份启动 —— 这三样都没用，SAC 都不看。它只有「打开 / 评估 / 关闭」三个状态，被拦的文件不能单独放行。

0.9 起：自动改用 JNA

从 Control Flex 0.9 起，随包的 cfx-gamepadjni 在同一个 JAR 里带了两套独立后端：JNI（我们自己的 DLL）和按符号名直接调用 SDL3 的 JNA。一个 JAR、一套公开 API，不需要改任何设置。

顺序是固定的：先试 JNI。如果 System.load 被拒绝，就在同一次 initialize() 里改用 JNA。JNA 自己的原生库 jnidispatch 从 1.8.9 起就在 Minecraft 的 classpath 上，被成千上万的程序用过，微软云端有它的信誉记录；我们的 gamepadjni.dll 根本不会被加载，SAC 也就没有可拦的东西。

回退成功时，日志长这样 —— 不是报错，只有一条警告和最终接手的那条后端： 

[gamepad-jni] JNI backend unavailable: java.lang.UnsatisfiedLinkError: ...\Temp\gamepadjni-1234\gamepadjni.dll: An Application Control policy has blocked this file
[gamepad-jni] binding=jna (SDL3 from ...\Temp\gamepadjni-1234)

这不是故障状态：任务管理器里不会出现 gamepadjni.dll，手柄照常工作。唯一少掉的是 SDL 自己的日志捕获，那只是诊断信息。枚举、热插拔、震动、电量、触摸板、传感器，全都一样。

你该做什么

  1. 更新到 Control Flex 0.9 或更新版本。0.8.9 及更早只有一条后端，被 SAC 拦下就等于完全没有手柄，部分版本还会崩溃。0.9 发布之前，唯一的临时办法是关闭 SAC —— 先看下面的代价。
  2. 1.7.10 要多做一步：这一版 Minecraft 不带 JNA，回退没有东西可绑 —— 见下一节。
  3. 想确认实际走的是哪条后端，用本页末尾的诊断开关，对比两行日志。

1.7.10：自己挂一个 JNA

Minecraft 1.7.10 的 classpath 上没有 JNA，所以即使在 0.9 上回退也无法生效。-Djna.library.path 解决不了这个问题 —— 那个属性只是告诉 JNA 原生库在哪，而且要在 JNA 的类已经加载之后才会读。

在 1.7.10 使用的 Java 8 上，把 JNA 的 jar 放到游戏类加载器能看见的位置： 

-Xbootclasspath/a:C:\path\to\jna-5.12.1.jar

Prism、HMCL 和官方启动器都接受把它写进 JVM 参数。路径要用绝对路径。这个选项只存在到 Java 8：用 Java 9+ 启动的 1.7.10 会直接拒绝，只能把 jar 放进启动器的 classpath。

任意 JNA 5.x 版本都可以（都是 Java 8 字节码）；核心 jar 就够，不需要 jna-platform。如果 JNA 解压不出自己的 jnidispatch，再用 -Djna.boot.library.path 指向存放 jnidispatch.dll 的目录。

架构不匹配

日志里出现 UnsatisfiedLinkError、又没有 Application Control 字样时，先怀疑架构：32 位 x86 的 JVM 仍会按 x86_64 去找库；Windows on ARM 上如果用 ARM64 的 JVM，而 JAR 里只有 x86_64 版本，同样找不到。

Windows 上一律用 64 位 x64 Java（含 Windows on ARM）。Android 的 ABI 与启动器要求见平台支持。

更新后还是失败呢

看 JNA: 那一行。如果它报的是 SDL3.dll 加载失败，很可能是 SAC 把 SDL3 也拦了 —— 同一个机制、同一个原因。JNA 回退只是把我们的 DLL 从名单里去掉，它没法替 SDL3 背书。

这种情况客户端已经没有绕法了。把日志发给我们，能捞到 CodeIntegrity 事件的话一并附上：我们可以确认被拦的是哪个文件；长期解法是给原生库做代码签名，这不是你这边能做的。报障清单在概览页。

关于关闭 SAC：这是设备级的选择，不是给某个游戏开的开关。很多机器关掉之后，要重置或重装 Windows 才能再打开。它不会让 Defender 失效，但确实少了一层防护 —— 这个决定该为整台电脑做，不是为一个模组做。

诊断开关

默认是 auto。写报告时 —— 或者想证明到底哪一半坏了 —— 可以强制走一条后端再对比： 

-Dcfx.gamepadjni.binding=jni     # JNI only, no fallback (reproduces a Smart App Control block)
-Dcfx.gamepadjni.binding=jna     # JNA only, JNI never attempted
-Dcfx.gamepadjni.binding=auto    # default: JNI, then JNA

jni 会直接失败而不是回退，正好用来复现 Windows 的拦截。jna 完全跳过我们的 DLL，用来看回退路径本身是否健康。系统属性优先于 CFX_GAMEPADJNI_BINDING 环境变量；大小写不敏感，不认识的值按 auto 处理。

手柄根本没被识别？看手柄未被识别。游戏启动就崩？看启动崩溃。报障清单在概览页。

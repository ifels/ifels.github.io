当 JSON 不够用：桥接模组

compat JSON 只能调整「已经存在的东西」—— 已注册的 KeyMapping、已派发的按键、已打开的界面。如果模组自己造了一套输入系统，就必须在 Java 侧接入：这就是桥接模组（bridge mod）。

一、先判断：到底该不该写代码

compat JSON 能做到 只有桥接模组能做到
把已注册的键位归到 Main / Screen / Overlay 让没有注册 KeyMapping 的按键出现在绑定列表里
选择派发通道（含 GLFW 轮询镜像） 接住直接调 GLFW.glfwGetKey 的模组（GLFW 层不可注入）
按主手物品 + 玩家状态压制动作 把模组的运行时状态推给 Control Flex 当条件用
相位保持、忽略键、提示文案、每页摇杆参数 读摇杆轴做完全自定义的逻辑（载具转向、镜头）
用虚拟键鼠兜底只认物理键的模组 告诉 Control Flex 「某个叠层现在到前台了」，切换摇杆行为

一句话判断：目标模组的按键能在「按键映射 → 该模组」里看到，就不需要桥接；看不到，才需要。

二、control-flex-api 是什么

  • 独立仓库 ControlFlexMC/control-flex-api，经 JitPack 发布，当前 0.9.0。
  • 编译产物是 Java 8 字节码，JVM 8+ 都能加载，桥接模组不必跟主模组用同一套工具链。
  • 只做 compileOnly：运行时由 Control Flex 本体提供，不要把 API 打进你的 jar。
  • 能力范围：读手柄、查动作状态、推模组状态、声明交互式叠层、安装 compat / guide 资源。
// build.gradle
repositories { maven { url 'https://jitpack.io' } }

dependencies {
    compileOnly 'com.github.ControlFlexMC:control-flex-api:0.9.0'
    compileOnly 'org.jetbrains:annotations:24.0.1'
}
# mods.toml（Forge / NeoForge）
[[dependencies.your_mod_id]]
    modId = "controlflex"
    mandatory = true
    versionRange = "[0.8.7,)"
    ordering = "AFTER"
    side = "CLIENT"

# fabric.mod.json
{ "depends": { "controlflex": ">=0.8.7" } }

第一行永远是可用性检查 —— Control Flex 可能没装，SDL3 也可能初始化失败。所有 provider 拿到的都可能是 null。 

if (!ControlFlexApi.isAvailable()) {
    return;   // fall back: skip every controller-related path
}

三、插件骨架：IControlFlexPlugin

回调 什么时候调用 / 干什么
getModId() 插件标识，用于日志与去重。
onInstallCompatConfigs() 在 ready 之前调用，用 installer.install() 把 compat JSON 装到 compat/mods/。
onInstallGuideAssets() 同上，装到 guides/mods/。
onControlFlexReady() 唯一的初始化回调，此时所有 provider 已就绪。
onControllerConnectionChanged() 手柄插拔时触发。
requireApiVersion() 默认方法，检查最小 API 版本，不满足返回 false。 
package com.example.mymod;

import com.ifels.controlflex.api.*;

public class MyPlugin implements IControlFlexPlugin {

    @Override
    public String getModId() { return "my_bridge_mod"; }

    @Override
    public void onInstallCompatConfigs(ICompatAssetInstaller installer) {
        installer.install("/assets/my_bridge_mod/compat/targetmod.json", "targetmod.json");
    }

    @Override
    public void onControlFlexReady() {
        if (!requireApiVersion("0.8.7")) return;
        if (!ControlFlexApi.isAvailable()) return;

        ControlFlexApi.getPlayerStateRegistry().setState("mymod:initialized", true);
    }
}

注册靠 SPI 服务文件，Control Flex 会自动发现： 

src/main/resources/META-INF/services/com.ifels.controlflex.api.IControlFlexPlugin

com.example.mymod.MyPlugin

安装的 JSON 落在 compat/mods/：优先级在 default/ 之上、user/ 之下 —— 所以玩家仍然可以用 user 层覆盖你装的默认值，不会被桥接锁死。

四、能拿到什么

接口 用途
IInputProvider · IControllerState 读摇杆轴、扳机、按键；IControllerState 是实时视图，跨 tick 缓存会读到旧值。
IControllerCapabilities 手柄硬件能力（型号、是否支持震动等），用来决定降级策略。
IActionStateProvider 查某个动作（内置或模组键）当前是否激活，ID 形如 attack / modid:key.name。
IPlayerStateRegistry 推 modId:stateName 状态，供 JSON 的 playerState 条件消费。setState 是唯一可以从任意线程调的。
IInteractiveContextRegistrar 声明自绘叠层的前台 / 后台，让 Control Flex 在被声明期间切到 Overlay 相位。
ICompatAssetInstaller 安装 compat / guide 资源（只在对应回调里可用）。

线程模型：除 setState() 外全部在客户端主线程调用；getActiveGameActions() 与 IControllerState 都是实时视图，不要跨 tick 持有。

五、现在有哪些官方的兼容实现

兼容实现分三类，源码都在 GitHub 的 ControlFlexMC 组织下：

仓库 类型 解决什么
control-flex 本体 内置 compat JSON + 派发通道 + 三层覆盖，覆盖绝大多数标准 KeyMapping 模组。内置 JSON 源码在 src/main/resources/controlflex/compat/。
cfx-compat-configs 配置源 社区配置的分发与共享，按 MC 版本 / 加载器组织，是「不用写代码」那条路的天花板。
cfx-compat-epicfight 桥接 Epic Fight 的战斗模式状态与专属键位；也是「状态推送 + 资源安装」最完整的样例。
cfx-compat-emi 桥接 EMI 把键位存在自己的配置里、不注册 KeyMapping；桥接注册 22 个伪 KeyMapping 再转发回 EMI 的交互函数。
cfx-compat-create 桥接 Create 列车控制台轮询原始键态（InputConstants.isKeyDown），模拟移动接管后没人发布键态，得由桥接补上。
cfx-compat-vehicles 桥接 沉浸车辆（MTS）直接调 GLFW.glfwGetKey；桥接把 mixin 放进车辆模组自己的读取路径（目前只支持 MTS）。
cfx-compat-exposure 桥接 Exposure 相机模组的键位与界面适配。

桥接与 JSON 不是二选一：多数桥接自己也会在 onInstallCompatConfigs 里装一份 JSON 到 mods/ 层 —— 把「键位怎么摆」交给 JSON，「运行时怎么算」留给 Java。

六、三种典型场景，三种做法

1）键位根本没注册：补一组伪 KeyMapping

模组把键位存进自己的配置文件、在自己的界面里匹配（EMI 就是这样），既不出现在原版控制里，也不会被自动发现。做法是注册一组普通 KeyMapping，再把「按下」转发回模组自己的交互入口 —— 不伪造输入，也不改模组的键位设置。 

// 示意：注册一组伪 KeyMapping（注册 API 随 MC 版本 / 加载器不同）
new KeyMapping("key.cfx_target.open", GLFW.GLFW_KEY_K, "key.categories.cfx_target");

// 每 tick 把 Control Flex 的动作状态转发回模组自己的入口
if (ControlFlexApi.getActionStateProvider()
        .isGameActionActive("cfx_target:key.cfx_target.open")) {
    TargetMod.openPanel();   // 调用模组自己的函数，而不是模拟按键
}

2）模组直接读原始键态：mix 到它的读取点

glfwPoll 通道能覆盖 InputConstants.isKeyDown 这类轮询；但直接调 GLFW.glfwGetKey 的模组读不到 —— GLFW 由系统类加载器加载，不经过 ModLauncher 的转换。办法是把 mixin 落到目标模组自己的读取入口上，回答「现在按着没有」。 

// 示意：只回答四个移动键，其余交还原逻辑
@Mixin(TargetInput.class)
public abstract class TargetInputMixin {

    @Inject(method = "isKeyPressed", at = @At("HEAD"), cancellable = true)
    private void cfx$steering(int keyCode, CallbackInfoReturnable<Boolean> cir) {
        if (ControlFlexApi.isAvailable()
                && ControlFlexApi.getActionStateProvider().isGameActionActive("move_forward")) {
            cir.setReturnValue(true);
        }
    }
}

把这种 mixin 关在独立的桥接模组里，核心就不必背第三方依赖，出问题也只影响这一个兼容包。

3）模组有运行时状态：推 state，让 JSON 消费

Epic Fight 的「战斗模式」决定了哪些按键该被模组接管。Java 侧只负责把状态推出去，具体压制哪些动作写进 JSON —— 玩家和包作者都能改。 

// Java：状态变化时推一次
ControlFlexApi.getPlayerStateRegistry()
    .setState("epicfight:battle_mode", inBattle);
// JSON：条件消费（主手拿武士刀且处于战斗模式时，压制通用 use）
"itemSuppressKeys": [
  { "item": "efn:yamato_dmc*",
    "playerState": ["epicfight:battle_mode"],
    "suppressActions": ["use"] }
]

七、调试与发布

  • 日志前缀 [ModCompat]：配置加载、覆盖、跳过原因都在这里；桥接自己的日志另开一个 logger。
  • 用 requireApiVersion("0.8.7") 守住最低 API 版本，并在 mods.toml / fabric.mod.json 里把 Control Flex 声明为 mandatory 依赖。
  • API 只 compileOnly；打包成独立 JAR，不要 shade 进去，否则会跟本体重复。
  • 发布时写清：解决什么、测试过哪些模组版本与加载器、有没有可选的 JSON 默认值。

桥接模组与开发接口

compat JSON 只能调整「已经存在的东西」—— 已注册的 KeyMapping、已派发的按键、已打开的界面。如果模组自己造了一套输入系统，就必须在 Java 侧接入：这就是桥接模组（bridge mod）。这一页是桥接开发的唯一入口：先判断该不该写代码，再讲 API、骨架、接口速查、官方实现与发布。

本页内容： 先判断 · API 接入 · 插件骨架 · 接口速查 · 官方实现 · 五种手法 · 调试与发布

一、先判断：到底该不该写代码

compat JSON 能做到 只有桥接模组能做到
把已注册的键位归到 Main / Screen / Overlay 让没有注册 KeyMapping 的按键出现在绑定列表里
选择派发通道（含 GLFW 轮询镜像） 接住直接调 GLFW.glfwGetKey 的模组（GLFW 层不可注入）
按主手物品 + 玩家状态压制动作 把模组的运行时状态推给 Control Flex 当条件用
相位保持、忽略键、提示文案、每页摇杆参数 声明「某个叠层 / 相机现在被模组接管了」，切换摇杆与视角行为
用虚拟键鼠兜底只认物理键的模组 读摇杆轴做完全自定义的逻辑（载具转向、镜头），或把动作转发回模组自己的函数

一句话判断：目标模组的按键能在「按键映射 → 该模组」里看到，就不需要桥接；看不到，才需要。三种手段是递进的 —— 自动发现 → compat JSON → 桥接，别跳过前两级直接写代码。

二、接入 control-flex-api

  • 独立仓库 ControlFlexMC/control-flex-api，经 JitPack 发布，当前 0.9.0。
  • 编译产物是 Java 8 字节码（class 52），JVM 8+ 都能加载，桥接模组不必跟主模组用同一套工具链。
  • 只做 compileOnly：运行时由 Control Flex 本体提供，不要把 API 打进你的 jar。
  • 能力范围：读手柄、查动作状态、推模组状态、声明交互式叠层、接管视角、安装 compat / guide 资源。
// build.gradle
repositories { maven { url 'https://jitpack.io' } }

dependencies {
    compileOnly 'com.github.ControlFlexMC:control-flex-api:0.9.0'
    compileOnly 'org.jetbrains:annotations:24.0.1'
}
# mods.toml (Forge / NeoForge)
[[dependencies.your_mod_id]]
    modId = "controlflex"
    mandatory = true
    versionRange = "[0.8.8,)"
    ordering = "AFTER"
    side = "CLIENT"

# fabric.mod.json (Fabric)
{ "depends": { "controlflex": ">=0.8.8" } }

第一行永远是可用性检查 —— Control Flex 可能没装，SDL3 也可能初始化失败。所有 provider 拿到的都可能是 null。 

if (!ControlFlexApi.isAvailable()) {
    return;   // Control Flex missing or not initialized: skip every controller path
}

三、插件骨架：IControlFlexPlugin

回调 什么时候调用 / 干什么
getModId() 插件标识，用于日志与去重。
onInstallCompatConfigs() 在 ready 之前调用，用 installer.install() 把 compat JSON 装到 compat/mods/。
onInstallGuideAssets() 同上，装到 guides/mods/。
onControlFlexReady() 唯一的初始化回调，此时所有 provider 已就绪。
onControllerConnectionChanged() 手柄插拔时触发。
cameraLookConsumer() 返回 ICameraLookConsumer 可接管每帧视角增量（0.8.8+，见相机接管）；返回 null 表示不接管。
requireApiVersion() 默认方法，检查最小 API 版本，不满足返回 false。 
package com.example.mymod;

import com.ifels.controlflex.api.*;

public class MyPlugin implements IControlFlexPlugin {

    @Override
    public String getModId() { return "my_bridge_mod"; }

    @Override
    public void onInstallCompatConfigs(ICompatAssetInstaller installer) {
        installer.install("/assets/my_bridge_mod/compat/targetmod.json", "targetmod.json");
    }

    @Override
    public void onControlFlexReady() {
        if (!requireApiVersion("0.8.8")) return;
        if (!ControlFlexApi.isAvailable()) return;

        ControlFlexApi.getPlayerStateRegistry().setState("mymod:initialized", true);
    }
}

注册靠 SPI 服务文件，Control Flex 会自动发现： 

src/main/resources/META-INF/services/com.ifels.controlflex.api.IControlFlexPlugin

com.example.mymod.MyPlugin

发现与回调的顺序（决定了你在哪个回调里能干什么）： 

Control Flex startup
  └── initializeClient()
        ├── providers injected  → isAvailable() becomes true
        └── built-in configs extracted to default/

  └── onKeyMappingsReady()
        └── discover SPI plugins
              ├── new CompatAssetInstaller(plugin.class, compatDir)
              ├── plugin.onInstallCompatConfigs(installer)
              ├── new CompatAssetInstaller(plugin.class, guideDir)
              ├── plugin.onInstallGuideAssets(installer)
              └── plugin.onControlFlexReady()

  runtime
        ├── plugin.onControllerConnectionChanged(connected)
        └── plugin.cameraLookConsumer().consumeLook(yaw, pitch)   // per frame, if non-null

安装的 JSON 落在 compat/mods/：优先级在 default/ 之上、user/ 之下 —— 所以玩家仍然可以用 user 层覆盖你装的默认值，不会被桥接锁死。同名文件按内容整体覆盖，不会做字段级合并。

ICameraLookConsumer（0.8.8+）

boolean consumeLook(float yaw, float pitch)
// true  = this frame's look is consumed: Control Flex must not write player rotation
// false = not consumed: Control Flex keeps its normal path
  • 用途：模组接管了渲染相机（Epic Fight 的 TPS 战斗视角、锁定目标等），此时玩家的 yRot/xRot 不再是画面来源，必须把视角增量转交给那个模组。
  • 每帧最多调用一次，参数是转向之前标定过的增量，与原版鼠标管线交给接管方的是同一个尺度。
  • 在插件里覆写 cameraLookConsumer() 返回实现；返回 null（默认）表示不接管。

IInteractiveContextRegistrar

void notifyOverlayForeground(String className)   // overlay entered the foreground
void notifyOverlayBackground(String className)   // overlay went back (pairs with foreground)
void clearAll()                                  // fallback: world unload / mod shutdown

className 是全限定类名 —— Control Flex 拿它去 compat JSON 的 overlay 表里查摇杆与光标行为。调用前先判空：getInteractiveContextRegistrar() 可能是 null。

ICompatAssetInstaller

// fileName:     target file name inside compat/mods/ or guides/mods/
// returns:      true when installed

五、现在有哪些官方实现

兼容实现分三类，源码都在 GitHub 的 ControlFlexMC 组织下：本体（内置 JSON + 派发通道）、配置源（社区 JSON 的分发）、桥接（真的写 Java 的那 5 个）。

cfx-compat-configs 纯 JSON 能覆盖的模组 按 ControlFlex 版本打 tag 社区配置源，见兼容配置
cfx-compat-epicfight Epic Fight 1.20.1 Forge · 1.21.1 NeoForge 注册为 EF 的手柄输入 mod + mixin 改绑定查找 + 状态推送 + 相机接管
cfx-compat-create Create 列车控制台 1.20.1 Forge / Fabric · 1.21.1 NeoForge 单个注入点，把移动脉冲并进按键判定
cfx-compat-exposure Exposure 取景器 1.20.1 Forge / Fabric · 1.21.1 Fabric / NeoForge 声明交互式叠层的前台 / 后台

cfx-compat-epicfight：把 Control Flex 变成 EF 的手柄后端

Epic Fight 不读 KeyMapping，它有一套自己的输入 SPI（IEpicFightControllerMod）：没人注册实现时，它会退回去查原始 GLFW 键盘状态 —— 手柄绑定永远满足不了。同时它按动作查 ControllerBinding，这个对象只能由实现方提供，JSON 给不出来。

所以这个桥接做三件事：实现 IEpicFightControllerMod（摇杆 → PlayerInputState，动作 → ControllerBinding）；用 mixin 覆写 EF 的 controllerBinding()，把绑定查找重定向到 Control Flex 的动作状态；监听 ChangePlayerModeEvent 推送 epicfight:battle_mode。此外 EpicFightCameraBridge 实现了相机接管 —— 把转向增量交给 EpicFightCameraAPI.turnCamera()，EF 接管视角时（TPS 战斗视角、锁敌）画面才跟手。

要求：ControlFlex ≥ 0.8.8；Epic Fight ≥ 20.14（1.20.1 Forge）/ ≥ 21.15（1.21.1 NeoForge）。与 Controlify 互斥 —— 两边都要当 EF 的手柄 mod，只能留一个。源码入口：CfxEpicFightControllerMod、EpicFightStateBridge、EpicFightCameraBridge、mixin/EpicFightInputActionMixin。

cfx-compat-create：一个注入点解决列车油门

Create 的列车控制台不读 KeyMapping.isDown()，而是一路问到 InputConstants.isKeyDown(window, code)。而 Control Flex 的模拟移动会接管 MOVE 组：动作不再派发，摇杆值直接写进 player.input.forwardImpulse —— 于是玩家在走，但「有键按下」这件事从来没被发布过，列车油门收不到。

做法克制到极简：只在 ControlsUtil.isActuallyPressed(KeyMapping) 的 RETURN 上注入一次，把 forwardImpulse / leftImpulse 并进「前进 / 后退 / 左右」的判定；sneak → 刹车、jump → 鸣笛。真实按键已经按下时原样返回，键盘优先级不丢。

注意它不写任何全局状态：不合成 GLFW 轮询、不写 KeyMapping、不发 Forge 按键事件，所以不会污染别的模组；也不需要判断「玩家是不是在开车」，因为 isActuallyPressed 只有列车控制台会调。源码入口：CreateTrainControl、mixin/ControlsUtilMixin。

cfx-compat-exposure：只做上下文声明

Exposure 的取景器是一个会夺走镜头、隐藏 HUD 的交互式叠层。Control Flex 只为它知道的上下文切换摇杆行为，所以桥接只负责通报：CameraClient.setupViewfinder / removeViewfinder 这两个所有开关路径的必经点上挂 mixin，调用 notifyOverlayForeground / notifyOverlayBackground。

细节在配对：桥接自己维护前台标志，没有活动取景器时 removeViewfinder 不会发出孤立的 background；切换相机会按 background → foreground 的顺序成对发出；退出世界时重置并补一次 background。要求 ControlFlex ≥ 0.8.7（0.8.7 重命名了这两个方法）、Exposure ≥ 1.9.20。

cfx-compat-emi：22 个伪 KeyMapping

EMI 把键位存在自己的配置（binds.*）里、在自己的界面里匹配，一个 Minecraft KeyMapping 都不注册 —— 所以它的动作既不出现在原版控制里，也不会被控制器的自动发现看到。桥接注册 22 个伪 KeyMapping 让 Control Flex 发现，按下时转发回 EMI 自己的交互函数：不伪造输入，也不改写 EMI 的键位设置。

分组 动作
界面打开 / 关闭 EMI、聚焦搜索、清空搜索
浏览查看配方 / 用途、加入收藏、配方树、物品树、前进 / 后退
合成合成一份 / 一组、送到背包（单份 / 整组）、送到光标（单份）
创造作弊给一份 / 一组到背包或光标
管理隐藏物品、按 ID 隐藏、复制配方 ID

全部落在 GUI 层，绑定列表里显示为「Control Flex x EMI」。多数动作作用于光标悬停的物品，所以要先指过去再按；输入框获得焦点、EMI 关闭或重载时只有「开关 EMI」有效。未支持：defaultStack、deleteCursorStack、showCraft（前两个是配方界面深处的内联逻辑，第三个是「按住状态」而不是动作）、displayAllRecipes（未进发布 jar）、配方界面上的「复制配方 ID」（上下文在私有字段里）。它也不会改写 EMI 自己的 binds.*。

cfx-compat-vehicles：载具只认 GLFW

沉浸车辆（MTS）用 GLFW.glfwGetKey(window, keyCode) 读操作，既不看 KeyMapping 也不看 InputConstants —— keyMapping / virtualKbm / glfwPoll 三个通道都够不到它。GLFW 层本身在 Forge 上不可注入（库类由系统类加载器加载，不经过 ModLauncher），所以 mixin 只能落在载具模组自己的读取路径里：InterfaceInputMixin 挂 mcinterface1201.InterfaceInput#isKeyPressed，四个移动键返回 true。

判断信号仍然是玩家自己的 forwardImpulse / leftImpulse（含模拟移动的曲线），为零时回落到动作状态，所以关掉模拟移动也能用；不轮询、不写全局键态、物理按键优先。不随包发 JSON：它直接读本体的信号，没有需要跟配置格式同步的规则集。已知限制：IV 自己的键位（car.gas 等）被忽略，改过就复位成 WASD；不要给 IV 绑内置手柄轴，那会置 kbOverride 并让桥接失效；mixin 目标是带版本号的包名（mcinterface1201），换 MC 版本必须重新构建。

桥接与 JSON 不是二选一：多数桥接自己也会在 onInstallCompatConfigs 里装一份 JSON 到 mods/ 层 —— 把「键位怎么摆」交给 JSON，「运行时怎么算」留给 Java。社区配置库里 create / emi 的配置还反过来用 dependencies 要求桥接已安装。

六、五种手法，五个真实例子

1）键位根本没注册：补一组伪 KeyMapping（EMI）

注册一组普通 KeyMapping 让自动发现看到，再把「按下」转发回模组自己的交互入口 —— 不伪造输入，也不改模组的键位设置。 

// Register a pseudo key mapping (registration API differs per MC version / loader)
new KeyMapping("key.cfx_target.open", GLFW.GLFW_KEY_K, "key.categories.cfx_target");

// Each tick, forward Control Flex's action state into the mod's own entry point
if (ControlFlexApi.getActionStateProvider()
        .isGameActionActive("cfx_target:key.cfx_target.open")) {
    TargetMod.openPanel();   // call the mod's function, do not synthesize a key press
}

2）模组直接读原始键态：mixin 到它的读取点（载具 / Create）

glfwPoll 通道能覆盖 InputConstants.isKeyDown 这类轮询；但直接调 GLFW.glfwGetKey 的模组读不到 —— GLFW 由系统类加载器加载，不经过 ModLauncher 的转换。办法是把 mixin 落到目标模组自己的读取入口上，回答「现在按着没有」。 

// Only answer for the four movement keys; everything else keeps the original logic
@Mixin(TargetInput.class)
public abstract class TargetInputMixin {

    @Inject(method = "isKeyPressed", at = @At("HEAD"), cancellable = true)
    private void cfx$steering(int keyCode, CallbackInfoReturnable<Boolean> cir) {
        if (ControlFlexApi.isAvailable()
                && ControlFlexApi.getActionStateProvider().isGameActionActive("move_forward")) {
            cir.setReturnValue(true);
        }
    }
}

把这种 mixin 关在独立的桥接模组里，核心就不必背第三方依赖，出问题也只影响这一个兼容包。

3）模组有运行时状态：推 state，让 JSON 消费（Epic Fight）

Epic Fight 的「战斗模式」决定了哪些按键该被模组接管。Java 侧只负责把状态推出去，具体压制哪些动作写进 JSON —— 玩家和包作者都能改。 

// Java: push once whenever the state flips
ControlFlexApi.getPlayerStateRegistry()
    .setState("epicfight:battle_mode", inBattle);
// JSON: consume it as a condition (holding a katana in battle mode: suppress generic use)
"itemSuppressKeys": [
  { "item": "efn:yamato_dmc*",
    "playerState": ["epicfight:battle_mode"],
    "suppressActions": ["use"] }
]

4）自绘叠层：声明前台 / 后台（Exposure）

自绘 HUD 不是 Screen，Control Flex 看不见它。打开、关闭时各通报一次，本体就会在 Overlay 相位里按 JSON 的 overlay 表切换摇杆与光标；类名要和 overlay 的键对齐。 

public final class OverlayNotifier {

    public static void onOpened(Object overlay) {
        IInteractiveContextRegistrar registrar = ControlFlexApi.getInteractiveContextRegistrar();
        if (registrar != null) {
            registrar.notifyOverlayForeground(overlay.getClass().getName());
        }
    }

    public static void onClosed(Object overlay) {
        IInteractiveContextRegistrar registrar = ControlFlexApi.getInteractiveContextRegistrar();
        if (registrar != null) {
            registrar.notifyOverlayBackground(overlay.getClass().getName());
        }
    }
}

成对通报是硬要求：只发 foreground 不发 background，摇杆行为会卡在叠层模式；退出世界时用 clearAll() 兜底。

5）模组抢了相机：接管视角增量

相机被接管后，写 yRot/xRot 不会改变画面。实现 ICameraLookConsumer，把增量交给接管方；返回 true 表示这一帧已经被消费，本体不再写玩家旋转。 

@Override
public ICameraLookConsumer cameraLookConsumer() {
    return (yaw, pitch) -> {
        if (!ControlFlexApi.isAvailable()) return false;
        return TargetCameraApi.getInstance().turnCamera(yaw, pitch);
    };
}

七、调试与发布

  • 日志前缀 [ModCompat]：配置加载、覆盖、跳过原因都在这里；桥接自己的日志另开一个 logger（LogManager.getLogger("my-mod-id")）。
  • 用 requireApiVersion("0.8.8") 守住最低 API 版本，并在 mods.toml / fabric.mod.json 里把 Control Flex 声明为 mandatory 依赖。
  • API 只 compileOnly；打包成独立 JAR，不要 shade 进去，否则会跟本体重复。
  • 目标模组尽量也 compileOnly（CurseForge Maven / Modrinth Maven），并在 mandatory 之外留一条「目标模组缺失就静默退出」的路径 —— 载具桥接就是这么做成「可有可无」的。
  • 多加载器项目用 common/ + forge/ + fabric/ 三模块：逻辑放 common，mixin 配置与 mod 元数据各写各的。
  • 发布时写清：解决什么、测试过哪些模组版本与加载器、有没有可选的 JSON 默认值、与哪些模组互斥。

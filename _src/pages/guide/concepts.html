Core Concepts

A handful of ideas this wiki builds on: actions and bindings, the seven-layer model, screens vs overlays, and where configs live. Reading this first makes every feature page shorter.

Actions & Bindings

  • Action: one bindable unit of function — jump, use_item, screen_menu_open_1, or a mod key like jei:key.jei.showUses. Every action belongs to a phase (in-game or GUI), and a binding table maps actions to controller buttons.
  • Binding: action + button + trigger mode (PRESS / HOLD / …, see Trigger Modes). The same button can fire different actions in different contexts — which is exactly why layers exist.
  • Templates & profiles: a template ships a whole default binding set; a profile is your own edits on top of it. Both live in Settings & Controls.

The Seven Layers

A standard pad has roughly a dozen inputs; a modpack can expose hundreds of actions. The seven-layer model lets one physical button mean different things per context — what a button does depends on which layer is currently active:

Layer Active when
Main Default in-game: movement, look, combat, hotbar, everyday mod actions
Shift 1–4 While the matching layer switch is held; four independent, fully explicit binding planes
Screen Whenever any screen is open: cursor, slot navigation, page switching, scrolling
Overlay While an interactive HUD is open; declared explicitly, no Main inheritance

Full defaults, editing rules and pitfalls: Seven Layers.

Screens vs Overlays

  • Screen: a state where gameplay stops — inventories, crafting, settings, mod UIs. While it is open the player cannot move or look; input switches to the Screen layer. Identified by the screen class's fully qualified name, e.g. net.minecraft.client.gui.screens.inventory.InventoryScreen.
  • Overlay: a state where gameplay continues — the player can still move and look while it is open. It may be a small HUD (spell wheels, third-party radial menus, photo HUDs) or cover the whole view; what makes it an overlay is that the game keeps running underneath. Declared by the class that opens it.
  • Input differs: the Screen layer ships full defaults (virtual cursor, slots, navigation, scrolling); the Overlay layer does not inherit Main — unconfigured actions stay silent, so a HUD cannot misfire combat keys.
  • In compat JSON they map to the screen / overlay sections (the overlay section does not support menus). See Mod Adaptation and Compat JSON.

Quick test: if you can still walk around while it is open, it is an Overlay; if world input stops the moment it opens, it is a Screen. The authoritative source is its compat declaration.

Where Configs Live & Who Wins

  • Keybindings: every version line uses config/controlflex/ as its root — templates/, profiles/, compat/, radial_menu/, guides/, keyboard/, backup/, all with the same layout.
  • Compat configs: four tiers, user > pack > mods > default; higher wins. The user layer lives at config/controlflex/compat/user/<mod_id>.json, and the in-game editors write into it. Details: Compat Overview.
